# T013 — Safety Gate Closure & Evidence

## Problem Statement

Sprint-03 retrospective (aes/sprints/sprint-03.md) identified a **safety gate bypass** in
the gRPC transport plus a **zero-evidence ticket close** for T011. "If it's not tested,
it's broken."

## Findings (hostile analysis)

### F-1 — gRPC `SendCommand` bypasses REQ-08 [CE-1, SEV-BLOCKER]
Evidence `src/dfb/grpc_service.py:351-356`:
```python
async def SendCommand(self, request, context):
    # Safety-critical command - would need token validation
    return flybrain_pb2.CommandResponse(success=True, message="Command '...' acknowledged (simulated)")
```
- HTTP `/command` (`service.py:542-567`) enforces `X-Confirmation-Token` (403 on missing/
  invalid) *before* acknowledging. The gRPC path acknowledges **with no gate at all**, and
  the comment "would need token validation" confirms the omission.
- Both transports currently *simulate* execution (no real MAVLink command path exists), so
  raw impact today = false assurance ("ARM ok" ≠ armed). The moment someone wires the gRPC
  command path to the FC command ground station, it becomes a remote, unauthenticated
  command surface.
- Violates REQ-08 and safety case SG3 (confirmation-token gate on all aircraft commands).

### F-2 — gRPC token semantics broken [CE-2, SEV-HIGH]
- `VerifyToken` (`grpc_service.py:347-349`) always returns `valid=False`.
- `IssueToken` (`grpc_service.py:342-345`) mints `uuid4()[:8]` into an independent store;
  HTTP's `_confirmation_tokens` (`service.py:52`) never sees it. A token issued over gRPC
  cannot validate anywhere; a token issued by HTTP validates only over HTTP.
- Client `GrpcDeckClient` therefore cannot round-trip issue→verify→command.

### F-3 — No test evidence for any gRPC RPC [CE-3, SEV-HIGH]
- grep for `grpc` in `tests/` and `sim/`: zero hits. T011 closed with zero automated tests.
- `grpc_service.py` (30.4%), `grpc_server.py` (23.3%), `pb2` (14.8%) uncovered.

### F-4 — HTTP routes / CLI equally unused by tests [CE-4, SEV-MED]
- `service.py` 43.1% (route handlers, token store untested), `cli.py` 0.0%.
- `crsf_ingest` watchdog path (FC-41) has no timing/expiry unit test (recorded N/A in T012).

### F-5 — gRPC server binds insecure `[::]:8083` by default [CE-5, SEV-MED]
- `grpc_server.py:35` `add_insecure_port(f"[::]:{port}")` unless `enable_tls=True`. Same
  default posture as HTTP, but the asymmetric danger is that gRPC carries an unguarded
  command stub on the same host.

### F-6 — repo hygiene [CE-6, SEV-LOW]
- T011+T012 uncommitted; scratch `fix_*.py`, `test_compile.py`, `test_parse.py`,
  `test_syntax.py`, `test_vulkan_*.py`, `debug_engine_layout.py`, `proto/` at root.

## Requirements (acceptance criteria)

- **AC-1** gRPC `SendCommand` can never silently succeed without the same confirmation-token
  gate as HTTP. Decision: remove the command surface from gRPC transport (see Decision D-1).
- **AC-2** gRPC `IssueToken`/`VerifyToken` share the HTTP token store and are correctly
  tested (round-trip: issue → verify → single-use consume → re-verify fails).
- **AC-3** Every gRPC RPC has automated test evidence: GetHealth, GetVersion, GetTelemetry,
  GetTelemetryStream (streaming, cancel), Decide, IssueToken, VerifyToken (+ SendCommand if
  kept).
- **AC-4** HTTP route handlers covered by tests verifying the token gate: `/confirm/issue`,
  `/command` (missing/invalid/valid token), `/confirm/verify/{token}`.
- **AC-5** CLI commands covered: health/version/decide/decide-telemetry/issue-token/
  command/verify-token/telemetry (transport selection, error paths).
- **AC-6** FC-41 (CRSF link watchdog) timing/expiry unit test added. N/A entry removed from
  traceability matrix where now automated.
- **AC-7** Repo hygiene: scratch files removed or moved to `scratch/` (gitignored);
  T011/T012/T013 changes committed behind an explicit human-approved commit (per CLAUDE.md).

## Non-goals

- No real MAVLink command execution path (FC still in "simulate + gate" posture).
- Vulkan (T005) still deferred.
- No gRPC TLS rollout (default posture stays insecure but command surface removed → the
  unsafe-command asymmetry disappears).

## Decision D-1 — gRPC transport scope (BLOCKER, needs human approval)

- **Option A (recommended): gRPC = advisory/telemetry-only.** `SendCommand` returns
  UNIMPLEMENTED from the servicer; `IssueToken`/`VerifyToken` removed or wired to shared
  store (verify-only useful). Commands stay HTTP-only behind the token gate. Smallest
  surface, matches existing precedent (`cli.py:58-60` "Legacy maze mode only supports HTTP
  transport"), zero new attack surface.
- **Option B: shared token store + real gate on gRPC.** Move `_confirmation_tokens` to a
  shared module; gRPC `SendCommand` requires the same single-use token; keep both
  transports able to command (still simulated). More code, two command paths to audit.
